1Threading architecture

One rule shapes the design: receive threads only receive and route; user threads execute. The C++ NDB API has its receive thread decode each signal and update the transaction, then wake the user thread, so once there are many user threads the receive thread becomes the bottleneck. Here a receive thread's work per signal is a table lookup and a copy into a page. Decoding rows, updating transaction state and running callbacks all happen on the user thread that owns the query, so that work grows with the application's threads rather than with a fixed pool.

The threads today Built

Orange lines carry transaction signals. A user thread writes its own requests to the socket; the send pool writes only what arrives while another thread is writing, and requests held back by adaptive send. Replies reach a user thread only through its inbox.

The rules that keep it fast

A node's state has one writer

Each node is assigned to one receive thread when the threads start, and stays there. That thread sees its socket close and executes its API_REGCONF, so it is the only writer of the node's published state. Everyone else reads atomics, and the state needs no mutex. Membership, which any receive thread may learn about from another node's NODE_FAILREP, is a separate word changed by compare-and-swap.

One lock per inbox per round

The router sorts a round's signals per user thread with no lock held, then posts each page under one short lock. A thread that gets a hundred signals in a round costs the receive thread one lock, not a hundred.

A thread is woken only when it sleeps

An inbox has a waiting flag that the user thread sets under the mutex before it sleeps. A post to a busy thread makes no system call. The wake-up is sent after the lock is released, so the thread never wakes into a mutex that is still held.

The thread that sends does the write

Each data node has one send buffer: the signals waiting to be written to its socket. A user thread appends its signals to it under the node's mutex. If no other thread is writing to that node, it marks itself as the writer, takes the buffer (swapping in an empty spare), releases the mutex and writes to the socket. Signals appended during that write are left for the send pool, so no thread keeps writing on other threads' behalf.

Failure checks cost one load

A process-wide link-event counter is raised whenever a link or a node's membership changes. poll runs the lost-link checks only when the counter has moved since it last looked.

Mutex levels, checked in debug builds

Dictionary (1), global (2), a thread's inbox (3), page pool (5), a node's send buffer (6). Locks are taken in rising order only. Levels 4 and 7 are empty because the C's receive-state and heartbeat mutexes are gone.

How it can evolve

These steps are listed in the order that would pay off first. Each one keeps the rule that receive threads only route.

  1. 1

    A wake-up descriptor in the poll set Planned

    A receive thread now waits in its poll set for up to 20 ms, so a newly connected link can go unwatched for that long. A self-pipe or eventfd would let a connect thread, or anyone else, wake it at once, and would remove the idle wake-ups.

  2. 2

    Executor threads that serve application threads Proposed

    Today every application thread that talks to RonDB is a user thread with its own block, capped at 256. An executor is a user thread that takes requests from any number of application threads through its inbox and pipelines them together. Section 3 describes it. It needs no new thread type in the library, only a second list in the inbox.

  3. 3

    More user threads Planned

    Phase 7 raises the user-thread limit from 256 to 4711, which widens the block-number space and the thread table. The limit of four management servers in a connect string stays. It matters for the synchronous model's first form (section 4), where every application thread holds its own connection.

  4. 4

    Wake-up helpers and more send threads Planned

    When one round wakes hundreds of sleeping user threads, the wake-ups themselves become the receive thread's cost. Helper threads could take over the wake-ups while the receive thread stays on the sockets. The send pool can likewise grow beyond one thread, taking nodes from a shared queue as it does now.

  5. 5

    Placing nodes on receive threads by load Planned

    Nodes are dealt to receive threads in turn when the threads start. With many data nodes and uneven traffic, placing them by measured load would balance the threads. Moving a node from one receive thread to another would need a hand-over that keeps the one-writer rule: stop the old owner reading, then install the link at the new owner.

2The data model

Everything a transaction needs while it runs lives in one user thread's ApidConnection and is never shared. Two kinds of data cross threads: requests appended to a node's send buffer, and replies coming back in a signal page. Neither goes through an allocation per signal or per transaction once the thread is warm.

Objects and who owns them Built

Shared: ApidGlobal → ApidShared

  • NodeShared per data node: published link state (atomics), membership word (compare-and-swap), link-drop request word, and the Sender. The Sender holds the waiting buffer, a spare buffer, the writer flag send_active, the deferred flag and the adaptive-send state, all behind one mutex.
  • ThreadTable: block number → inbox, with a change counter so that receive threads keep their own copy.
  • The send pool, the dictionary cache (TableDefs by name, as Arc, dropped on ALTER_TABLE_REP), the configuration.

Per user thread: ApidConnection

  • inbox: an Arc<ThreadConnection>, with the pages it gives back.
  • queries, transactions: generational object maps (PtrArray), handled by QueryId and TransId.
  • tc_records with a free list per node; active, a vector indexed by a record's place and holding the transaction that uses it.
  • outgoing per node: words, staged and cancelled; to_send, the transactions with something staged.
  • executed queue, spare query lists, fragment assembler, expected replies.

ApidQuery: one key operation, reused

Holds a table, a key record and an attribute record, and owns the rows they lay out: the application fills key_row_mut() and reads attr_row(), and nothing in the library points into the application's memory. Its per-run state, Execution, holds the transaction id every reply must carry, where its packed request lies (Staged), what the coordinator confirmed, and how much row has come.

Idle → Defined → Sent → Completed → Idle. A completed query goes to executed, or its callback runs and may define it again at once.

Transaction: local until its first send

Holds the transaction id, the TcRecord seized at the coordinator the hint chose, and the defined and sent query lists with their counts. It also holds the end wanted (commit or rollback), the error and the GCI.

The data node knows nothing about it until the first operation goes with the start flag. It is done when it has committed or rolled back and every sent operation is complete. Its record then returns to the free list, and its query lists are kept for the next transaction.

The block number (0x8000 + thread id) chooses the user thread. The receive thread reads nothing else. Block numbers are handed out in rotation, so that a late reply to a thread that has exited rarely reaches the thread that took its number. When one does, the id checks above reject it.

The send path: pack at define, patch at send Built

  1. a

    Define

    read_key or write_key hashes the key when the transaction has no coordinator yet, picks the node and takes a free TC record for it (seizing one only if none is free). It then packs TCKEYREQ with its key and attribute info straight into that node's staged buffer. The query remembers where its request lies (Staged { node_id, generation, at, len }).

  2. b

    Send

    send_queries walks to_send and sets the start, execute and commit flags in place: the last request of each transaction's batch gets execute, and gets commit too if the batch commits. It then moves each node's staged buffer to words, behind any commit acknowledgements waiting there. A request cancelled by a rollback before the send is cut out using cancelled.

  3. c

    Write

    NodeShared::send_words appends the node's words to the Sender under its mutex. If no other thread is writing to that node, this thread marks itself as the writer, swaps the waiting buffer with the spare, and writes outside the mutex. The result is one socket write per node per send, carrying every transaction's requests. Adaptive send may hold a small write back for company, and the send pool ends that wait when it is due.

The receive path: pages that go round Built

A small signal is copied into the user thread's page, so the page is released on one thread. A large TRANSID_AI stays in its receive page, which stays sealed until the user thread gives its signal page back. Every page is allocated and freed on the thread that owns it.

The receive thread reads a socket again, up to four times, while each read fills all the room it had, then moves on. Commit acknowledgements the replies call for are queued in outgoing and leave with the next send. They are written on their own only after waiting 1 ms, or when nothing is in flight.

Memory rules

  • No allocation per transaction or per signal once warm. Query lists of closed transactions are kept (up to 8192 spare), TC records are reused through free lists, send buffers are swapped rather than reallocated, and signal pages keep their largest size.
  • Inline buffers spill; they never refuse. A TCKEYCONF with more than 16 operations goes on into a vector beside the inline array, and node lists hold eight inline. A protocol limit read from the data node's code is not a guarantee.
  • No unsafe on the row path. Queries own their rows, so the library never holds a pointer into the application's memory between send and completion. The C binding copies or maps the caller's rows onto them.

3The asynchronous programming model

Asynchronous is the primary model. A thread defines work, sends it, does something else, and collects results as they arrive. Throughput comes from having many operations in flight per thread. Latency matters less once the pipeline is full.

Pipelines on one thread Built

// once
let q = conn.create_query(&table, &key_rec, &attr_rec)?;
// per batch: define many, send once per node
let t = conn.start_transaction(hint, &table)?;
conn.read_key(q, t, &ReadKeyArgs { callback: Some(on_row), user_ref, .. })?;
// … more read_key / write_key, on this and other transactions
conn.commit_transaction(t)?;
conn.send_queries(false)?;
loop {
    conn.poll(10);          // callbacks run here; each may define the next batch
    while let Some(id) = conn.get_next_executed_query() { /* queries without a callback */ }
}

A callback runs inside poll on the polling thread, after the query has left its transaction's lists. It may define queries, start and commit transactions and send, which is how a pipeline keeps depth batches in flight. ic_bench works this way. The limitation is that new work can only come from this thread: from its own loop, or from a callback reacting to a reply. An application whose requests arrive on other threads, such as a network server's handlers, has to hand them to this thread somehow, and poll knows nothing about such hand-offs.

An executor with two inputs Proposed

An executor is a user thread that runs RonDB work for other threads. It must accept new queries while earlier ones are still in flight, so it listens to two interfaces:

From the data nodes, through a receive thread

Replies routed by block number into signal pages, as today. They complete operations, free coordinator records and make room in the pipeline.

From application threads

Requests such as "read this key", "run this transaction" or "write these rows", each with a way to deliver its result back. They fill the pipeline.

Both inputs arrive in the same inbox, under the same mutex, with the same waiting flag. The executor waits in one place and wakes for whichever comes first.

Why both inputs must share one wait point

A thread that sleeps can sleep on only one thing. If replies arrive on a condition variable and requests on a channel, the executor must either poll one while sleeping on the other, which adds latency or spins, or run a second thread that forwards one into the other, which adds a wake-up to every request. The inbox already has what is needed: a mutex, a condition and a flag saying the owner is asleep. Adding a second list lets either producer wake the executor with the rule that exists today, wake only if waiting, after releasing the lock:

struct Inbox {
    pages:    Vec<SignalPage>,   // from receive threads (today)
    spare:    Vec<SignalPage>,
    requests: Vec<Request>,      // from application threads (new)
    waiting:  bool,              // the executor sleeps on `cond`
    closed:   bool,
}

// application side, any thread; a Submitter is a cloneable handle on the inbox
fn submit(&self, r: Request) -> Result<(), Busy> {
    let wake = {
        let mut ib = self.inbox.lock();
        if ib.requests.len() >= self.limit { return Err(Busy); }
        ib.requests.push(r);
        std::mem::take(&mut ib.waiting)
    };
    if wake { self.cond.signal(); }
    Ok(())
}

The receive thread's post and submit are the same shape: append under a short lock, then wake the executor only if it was asleep. exchange, which already swaps emptied pages for posted ones, would also swap the request vector with an empty one, so the executor takes everything in one lock.

The executor's loop

loop {
    // 1. one lock: posted pages out, emptied pages back, requests out.
    //    Sleeps only if nothing is posted, no request waits,
    //    and nothing held back needs sending.
    let got = inbox.exchange(wait, &mut pages, &mut requests);

    // 2. replies first: they complete operations and free records
    for signal in pages { conn.receive_view(&signal); }

    // 3. completions go back to their application threads
    while let Some(done) = conn.next_completed() { done.deliver(); }

    // 4. admit new work while the pipeline has room
    while conn.in_flight() < limit {
        let Some(r) = requests.pop_front() else { break };
        r.define_on(&mut conn);   // start, read_key/write_key, commit
    }

    // 5. everything admitted this pass: one write per node
    conn.send_queries(false)?;
}

Replies are handled before requests are admitted. That frees coordinator records and pipeline room first, and a completion is delivered as early as possible. All requests admitted in one pass share one socket write per node, so the per-batch costs in chapter 12's model (a write, a read and a round per node) are spread over every application thread that submitted in that interval. Under load, batching comes on its own. Under light load a request goes out alone, as it should.

Back-pressure, delivery and failure

Back-pressure in two places

The request list is bounded: submit returns Busy, or blocks in a blocking variant, when it is full. Admission is bounded by the executor's in-flight limit. A request not admitted stays in the executor's local queue, in order, so a burst is absorbed without holding the inbox lock.

Delivering the result

Each request carries its completion: a slot plus a wake-up for a blocking caller, a callback run on the executor, or, in a Rust async layer, a Waker. The result is copied out of the query's attribute row into the slot, so the query is free for the next request at once.

Failure and timeouts

A node failure fails the transactions it affects, as today, and their requests complete with that error. Nothing is lost silently. A request can carry a deadline. The executor checks it when admitting, and fails a request that is still waiting after its deadline without sending it.

How many executors

One executor per core the application gives to RonDB work, each with its own block and TC records. Application threads pick one by key hash or round-robin. Executors share nothing but the nodes' send buffers, so they scale as user threads do today.

What the hand-off costs. With the Mac calibration of chapter 12, waking a sleeping thread costs about 8 µs of latency and 3 µs of CPU. An application thread that submits to a busy executor pays no wake-up. One that blocks for its result pays one wake-up when the result comes back. At a few hundred operations per batch that cost is a small share of each operation. For a single operation on an idle system it is comparable to the round trip itself.

4The synchronous programming model

Many applications want to write let row = read(key)? and carry on. Two forms can give them that, and they suit different workloads.

A · Each thread owns a connection Built

The application thread is a user thread. A synchronous call is define, send, then wait for that one reply. flush(ms, force) and call/wait_for already do this, and other requests the thread has in flight are served while it waits.

let t = conn.start_transaction(hint, &table)?;
conn.read_key(q, t, &args)?;
conn.commit_transaction(t)?;
conn.flush(1000, true)?;      // returns when done
let row = conn.query(q).attr_row();
  • Nothing between the caller and the socket: the lowest latency for one operation.
  • Throughput per thread is 1 / round trip. It scales only with threads, and each thread is a block (256 today, 4711 planned) with its own TC records.
  • Replies still go through the receive thread and the inbox, so each call costs one wake-up.

B · A blocking façade over executors Proposed

The application thread holds only a Submitter. A synchronous call submits a request to an executor (section 3) and sleeps on its own completion slot until the executor delivers the result.

let row = rondb.read(&table, key)?;   // submit + wait

// inside: submit, then
let mut s = slot.lock();
while !s.done { s = slot.cond.wait(s); }
  • Any number of application threads, with no block number each. Thousands of blocking callers share a few executors.
  • Requests from different callers are batched together, so under load the cost per operation falls to that of the pipelined model.
  • Costs one extra hand-off, application thread → executor, and back.

All three rest on the same core: an ApidConnection polled by the thread that owns it, with receive threads that only route. Form A exists today. Form B and the asynchronous executor need the same addition: a second list in the inbox, under the same lock and wake rule as the first. Once that is built, the C ABI can offer blocking calls to languages whose threads are cheap to block (C, C++, Java, Go through cgo), and a Rust async layer can hand out Futures from the same executors.
