# 04 — API design: Rust and C

This chapter describes the Data API as built in phases 1–6 (`ic_apid`)
and the C ABI that wraps it in phase 7 (`ic_capi`, built as
`libiclaustron`, with its header `include/iclaustron/ic_apid.h`
generated by cbindgen), with the executors of phase 8.1. The Phase 0
header was written before the code and differs from it; this chapter
replaces its design with what was built (rewritten 2026-10-14). The C++ header and bindings in other
languages are later (chapter 06, "Later"; Q6).

## Three layers, one implementation

| | Rust (`ic_apid`) | C (`ic_capi`) |
|---|---|---|
| Object | `ApidConnection` | `IC_APID_CONNECTION*`, opaque |
| Query, transaction | `QueryId`, `TransId`, in the connection | `IC_QUERY_ID`, `IC_TRANS_ID`, `uint32_t` |
| Method | `conn.read_key(q, t, &args)` | `ic_apid_conn_read_key(conn, q, t, &args)` |
| Error | `Result<T, IcError>` | `int32_t`, 0 or the error code, and `ic_error_*` |
| Callback | `fn(&mut ApidConnection, QueryId, usize)` | `void (*)(IC_APID_CONNECTION*, IC_QUERY_ID, void*)` |

The Rust API is the implementation. The C ABI is a thin wrapper: one
exported function per method, null checks, `catch_unwind` on every
entry, nothing on the hot path that the Rust call does not do. Other
languages bind the C ABI.

## The Rust API as built

### Starting

`ApidGlobal::connect(connect_string, node_name, &options)` parses the
connectstring, asks a management server for a node id and the
configuration, and starts the threads: connect threads, receive threads,
the heartbeat thread and the send pool. It returns at once; the data
nodes are connected in the background, and
`wait_for_first_started(ms)` and `wait_for_all_started(ms)` wait for
them. `ApidGlobal::start(config, mgm, ...)` is the same with a
configuration already fetched (`ic_apic::mgm_client`), as the tools do.

The connectstring: `host[:port]` items separated by commas (default
`localhost:1186`), `nodeid=N` to ask for that node id rather than one
the management server chooses, `bind-address=host` for the local
address. `GlobalOptions`, fixed for the life of the global:
`receive_threads` (1), `reply_wait_ms` (0: from the configuration, see
05 §6.9), `mgm_timeout_ms` (30 000). Stopping or dropping the global
stops every thread and waits for each.

One cluster per global (Q3, applied 2026-10-14): an application that
talks to several clusters makes several globals.

### Connections

`global.create_connection()` makes an `ApidConnection`: one user
thread's view of the cluster, with its own block number, inbox,
coordinator records, queries and transactions. It is `Send` and not
`Sync`: any thread may use it, one at a time. Everything a transaction
does happens on its connection; a transaction is never shared between
connections (joinable transactions dropped, Q4, applied 2026-10-14).

### Tables and indexes

`conn.table_bind(db, table)` gives an `Arc<TableDef>`; `index_bind(db,
index, table)` an `Arc<IndexDef>` (a MySQL server names a unique index
`name$unique`). The descriptions are cached for every connection of the
global. A table or index found out of date by a data node (241, 284) is
let go of, so the next bind fetches it again; `table_unbind` lets go of
it at once. `TableDef` gives the table's name, id, version, fields by
id and by name (`ColumnProps`: type, length, character set, nullable,
key, storage), whether it has blob columns, and its hash map;
`IndexDef` its own table (`as_table`), its base table and whether it is
unique; an index that is not online is refused at bind (7154).

### Records

A record describes a row as the application lays it out, a C struct for
example:

```c
struct my_row {
  uint32_t a;            /* key, INT UNSIGNED NOT NULL           */
  uint32_t b;            /* INT UNSIGNED, nullable                */
  uint8_t  name_len;     /* VARCHAR(20): 1 length byte, then data */
  char     name[20];
  uint8_t  null_bits;    /* bit 0 = b is NULL                     */
};
```

declared once with one `FieldSpec` per field (field id, offset, and
for a nullable field the byte and bit of its null bit), and the row's
size: `Record::new(&table, &specs, row_size)`.

- Values are stored as NDB stores them, so nothing is converted on the
  way: fixed-size fields inline at their offset with their NDB size,
  VARCHAR and VARBINARY a length byte (two, little-endian, for the long
  forms) and the bytes, the row reserving the longest.
- Values and null bits are checked bit by bit for overlap, as the
  reference checks; a NOT NULL field's null bit is ignored, as there.
- `Record::default_for(&table, ids)` lays a record out for the
  application: null bits first, eight to a byte, then the fields in
  attribute order, each on a 4-byte boundary, eight-byte integers and
  doubles on eight, the row rounded to eight bytes. Without ids it takes
  every field but the blob columns.
- A record naming a blob column is refused (`IC_ERROR_NOT_SUPPORTED`);
  blob columns wait for later (chapter 06).
- A record over the key fields serves as a key record; one covering
  every key field serves as key and attribute record alike.
- `text_row::put_value` and `value_text` put a value given as text into
  a row and give it back as text, for tools and examples. A character
  string is converted to and from its column's character set through
  tables compiled in from public standards (chapter 09): UTF-8 for
  utf8mb4, and for utf8mb3 the Basic Multilingual Plane; UTF-16 for
  utf16 and utf16le; UCS-2 and UTF-32, big-endian; and CP1252, as
  Unicode publishes it, for latin1. Which set a column is in comes from
  the data nodes: binding describes each character column's collation,
  once a collation for the process, without its weights unless it
  places a key (built 2026-10-16). A column of another set is shown and
  given as `0x` and hexadecimal digits, a CHAR padded with the pad byte
  the description names; a column whose collation could not be
  described is shown in hexadecimal and takes no text. A character the
  set cannot hold is refused; bytes that are not a string of the set are
  shown in hexadecimal. A CHAR is shown without its trailing spaces, a
  VARCHAR with them.

### Queries

A query lives in its connection and is named by a `QueryId`:
`conn.create_query(&table, &key_rec, &attr_rec)`, or
`create_unique_query(&index, &key_rec, &attr_rec)` for one through a
unique index; `free_query(id)` when idle. **A query owns its rows**,
sized by its records: the application fills `key_row_mut()` and, for a
write, `attr_row_mut()`, and reads `attr_row()` once the query has
completed. Nothing in the library points into the application's memory
while a query is out. A query is idle, defined, sent or completed, and
gives its error and the error's data (such as the index a duplicate key
names, 893) once completed.

### Defining

`conn.read_key(q, t, &ReadKeyArgs)` and `conn.write_key(q, t,
&WriteKeyArgs)` define a query on a transaction. The request is packed
then, into the connection's staged buffer, and goes with the next send.

- `ReadKind`: `Simple`, `Locked`, `Exclusive`, `Committed`,
  `ExclusiveNoWait`; through a unique index the coordinator takes a
  shared lock for a simple or committed read (05 §6.8).
- `WriteKind`: `Update`, `Write`, `Insert`, `Delete`. An insert or write
  through a unique index is refused, and so is an update through one
  whose values hold an indexed column (Q12). A delete on a table with a
  blob column is refused until blobs are built.
- `AbortOption`: `Default` (abort on error for a write, ignore it for a
  read), `AbortOnError`, `IgnoreError`; a committed read only ignores.
- `BatchHint`: `None`, `Safe`, `Unsafe` (bits 22 and 23 of the request).
- `user_ref` and `callback`: see below. `binding` is a word for a
  language binding's own use, read back with `query.binding()`; the C
  ABI keeps the C callback there. Rust callers leave it 0.
- Every row size a table can hold is written: a request too large for
  one message goes as a train of fragments (05 §2.2).

### Transactions

`conn.start_transaction(hint, table)` is local; the transaction begins
at the coordinator with its first query. The hint chooses the node:
`TransactionHint::Any` (the next started node in turn), `Node(id)`, or
`Partition(p)` from `conn.hint_for_key(&table, &key_rec, key_row)`,
which hashes the key as the data nodes do (05 §6.3, every claimed
character set and collation) and picks the partition's primary, or any
replica for read-backup and fully replicated tables. For a transaction
that starts with a unique-key query, `hint_for_unique_key(&index, ...)`
with the index's own table.

`commit_transaction(t)` and `rollback_transaction(t)` ask for the end;
it goes with the next send, on the last query defined and not sent or
as a request of its own. A transaction is done when it has ended and
every query has completed; `close_transaction(t)` lets it go. It
reports its `CommitState` (`Started`, `CommitRequested`,
`RollbackRequested`, `Committed`, `RolledBack`), its error and the
error's data, and the global checkpoint a commit belongs to. Node
failure: a lost coordinator's transactions are taken over by another
node, and a commit it finished is reported committed. A transaction
whose replies stop coming ends with 4012, its outcome unknown
(05 §6.9).

### Sending, polling and completion

`conn.send_queries(force)` sends everything defined and every end asked
for, one socket write per node; without `force` the adaptive send may
hold a node's write back for a moment to go with other threads'.
`conn.poll(ms)` takes what arrived and completes queries;
`conn.flush(ms, force)` is both. A completed query with a callback has
it called, on the polling thread, from inside the poll, with the
connection, the query and its `user_ref`; the callback may define
queries and start, commit and send transactions, and a poll from
inside it does nothing. A query without a callback goes on the executed
list, `conn.get_next_executed_query()`. No signal, fragment or signal
number reaches the application: a reply in fragments is joined inside
the poll (chapter 02).

### Synchronous helpers

`key_op::read_committed`, `read_unique_committed` and `write_key` do one
query as its own transaction, wait for it and give the row back in the
application's buffer: the synchronous style, with a connection per
thread.

### Executors (phase 8.1)

An application thread with no connection of its own runs key operations
through an executor (`ic_apid::executor`): a user thread of the
library's, with a connection, that takes requests from any number of
threads and runs them together. Everything it admits in one pass of its
loop goes in one write per data node, so the more threads call at once,
the more each send carries (doc/rust/architecture.html, section 3).

```rust
let mut executor = Executor::start(&global, &ExecutorOptions::default())?;
let mut submitter = executor.submitter();          // one per thread
let table = submitter.table_bind("ic_ex", "t1")?;  // bound on the executor
let rec = Record::default_for(&table, None)?;
let shape = OpShape::new(&table, &rec, &rec)?;     // made once
let mut request = Request::with_op(KeyOp::read(&shape, ReadKind::Committed));
// ... the key into request.ops_mut()[0].key_row_mut() ...
submitter.execute(&mut request)?;                  // blocks until it ends
let row = request.ops()[0].attr_row();
```

- **A request** (`Request`) is a transaction of key operations
  (`KeyOp`), defined together with the commit on the last, and sent
  together: it commits, or rolls back as a failed write or the
  coordinator decides. It is placed by its first operation's key unless
  given a hint. A request owns its rows, as a query does, and is used
  again and again: submitting resets its outcome.
- **A shape** (`OpShape`) is a table, or a unique index of it, and the
  records of an operation's rows: the executor's form of a query, made
  once and shared. The executor keeps queries of each shape it has run,
  copies a request's rows into one and the row read back out, and lets
  them go once nobody holds the shape.
- **Completion** (`Done`): the request is left in a `Slot` for a thread
  that waits on it, or handed to a `RequestCallback`, a plain function
  and a `usize` as every callback of the library is, on the executor's
  thread. `Submitter::execute` is the blocking form (form B of section
  4): it submits and sleeps on its submitter's own slot; give each
  thread its own submitter, by `executor.submitter()` or by cloning
  one. `submit` refuses a full inbox with `IC_ERROR_EXECUTOR_BUSY`, and
  `submit_wait` waits for room.
- **Limits**: at most `in_flight` requests out (400 by default), each a
  transaction with a record at its coordinator; at most `queue` waiting
  in the inbox (4 000). A request may carry a deadline
  (`set_timeout_ms`), checked when its turn comes: past it, it comes
  back with `IC_ERROR_TIMEOUT`, unsent.
- **Failures**: a node failure fails the transactions it affects, and
  their requests come back with the error, as on a connection.
  `Executor::stop` (or dropping it) fails what waits with
  `IC_ERROR_EXECUTOR_STOPPED`, finishes what is out and waits for the
  thread; a stopped executor's submitters refuse, handing the request
  back. Tables and indexes are bound through the submitter, which the
  executor does on its connection, waiting for the dictionary meanwhile.

A request is a transaction run start to end; a transaction that reads,
decides and then writes takes two requests, or a connection of its own.
Asynchronous calls for C, and Rust futures over the same executors, are
for later.

### Scans (phases 8.3 and 8.4; agreed with the author 2026-10-16)

A scan lives in its connection, named by a `ScanId`, and is made once
and run many times, as a query is: `conn.create_scan(&table, &rec)`,
over a table, with the record its rows are read into. **A scan owns
its row**, sized by its record, as a query owns its rows.

```rust
let scan = conn.create_scan(&table, &rec)?;
conn.start_scan(scan, &ScanArgs {
  lock: ScanLock::Committed,         // Committed, Shared or Exclusive
  ..ScanArgs::default()
})?;
conn.send_queries(false)?;            // the request goes with the next send
while !conn.scan_done(scan) {
  conn.poll(100);
  while let Some(batch) = conn.get_next_scan_batch() {
    while conn.next_scan_row(batch)? {
      let row = conn.scan_row(scan);  // laid out by the record
    }
    conn.release_scan_batch(batch)?;  // that receiver goes on
  }
}
```

- **`ScanArgs`**: `lock` (`Committed`, `Shared`, `Exclusive`);
  `trans`, for a locking scan whose rows may be taken over (8.5): the
  transaction they are taken over into, on the same connection. The
  scan then runs at that transaction's coordinator, under its id.
  Without it a scan needs no transaction at all, runs under an id of
  its own and takes over nothing, its locks held only while a batch is;
  a committed read never names one, as its rows cannot be taken over.
  `parallelism`, 0 for every fragment; `batch_rows` and
  `batch_bytes`, 0 for the configuration's (parameters 802 and 801),
  kept within 992 rows for a locking scan and 4 000 for committed
  reads; `partition`, to scan one partition by its id; `user_ref`,
  `callback` and `binding`, as for a query; `timeout_ms`, past which
  the scan is closed with `IC_ERROR_TIMEOUT`.
- **Batches** (`ScanBatchId`): each receiver, one per fragment scanned
  in parallel, delivers its batch when the whole of it has come, onto
  the ready list (`get_next_scan_batch`) or to the scan's callback,
  `fn(&mut ApidConnection, ScanBatchId, usize)`. The rows are copied
  out of the receive pages, so a batch held for as long as the
  application likes holds no page. `next_scan_row` unpacks the batch's
  next row into the scan's row, and `next_scan_row_into` into a buffer
  of the caller's, a copy less; rows stay packed until they are read,
  so a scan closed early pays only for the rows it read.
  `release_scan_batch` hands the batch back, and only then is that
  receiver asked for more: the consumer sets the pace, receiver by
  receiver. A batch not handed back stalls its receiver, and a locking
  scan's batch keeps its locks until the coordinator ends the scan
  (296). The synchronous `next_row` of 8.4, a row stream that hands
  batches back as it goes, is built on these, and is how an ordered
  scan is read, since its rows are merged across receivers.
- **Why so** (the author, 2026-10-16, choosing among alternatives): a
  scan made once and run many times allocates nothing after its first
  run; the batch is the protocol's unit of flow control, so memory
  stays within the parallelism times the batch bytes and a slow
  consumer slows only its own scan; and handing a batch back is what
  releases its locks, so a takeover (8.5) is placed before it. Reading
  rows in place in the receive pages was ruled out: a parked scan
  would hold pages every thread of the process needs.
- **The end**: a scan is done when every receiver has given its last
  batch and each has been handed back, or when it fails. `close_scan`
  ends it at any time: it waits for the batches asked for, then stops
  (chapter 05 §7.2). A done scan gives its error, none if it read to
  the end; `free_scan` once it is not running.
- **Errors** are the scan's: 274 and 266 for locks, 296 for a scan
  idle too long at the coordinator, 270 when a reading node fails
  (temporary: the scan is started again and its rows come again; in
  the error table since 2026-10-17), 4028 when the coordinator's node
  fails.

The synchronous form, scans through an executor, and the C ABI are
phase 8.4, below.

### Consuming scans (phase 8.4; built 2026-10-16)

Three ways to read a scan, all over the batches above.

**Synchronous, on a connection.** `next_row` reads a scan as a
stream of rows, and hands each batch back once its rows are read:

```rust
conn.start_scan(scan, &ScanArgs::default())?;
while conn.next_row(scan)? {           // Ok(false): read to the end
  let row = conn.scan_row(scan);
}
```

- `next_row(scan)` unpacks the next row into the scan's row, and
  `next_row_into(scan, row)` into a buffer of the caller's. When the
  batch it reads from is used up, it hands it back, so that receiver
  goes on, and takes the scan's next complete batch. While none is
  complete it sends what is due and polls. Every other scan and
  query of the connection is served meanwhile: their callbacks run,
  and their batches go on the ready list. It gives `Ok(false)` once
  the run is done with no error, and the run's error once it has
  failed. Rows of batches not yet read are then dropped, as for any
  failed run.
- `next_batch(scan)` gives the scan's next complete batch, waiting as
  `next_row` does, or `None` at the end. The application reads it
  with `next_scan_row` and hands it back itself, so it may hold
  several at once.
- **Where the batches come from**: a scan with no callback puts its
  batches on the connection's ready list, as in 8.3. `next_row` and
  `next_batch` take the oldest of that scan's batches and leave the
  other scans' batches there. A thread with one scan at a time finds
  its batch first in the list.
- A scan with a callback is refused (`IC_ERROR_NOT_SUPPORTED`). So is
  a wait inside a callback, where a poll does nothing; a batch that is
  already complete can still be read there.
- The wait lasts as long as the run goes on. The run's `timeout_ms`,
  the coordinator's own timers and node failure handling bound it
  (8.3).
- An ordered scan (8.7) is read only this way, `next_row` merging the
  rows of its receivers.

**Through an executor.** A thread with no connection of its own runs
a scan on an executor and reads the rows with a reader:

```rust
let shape = ScanShape::new(&table, &rec)?;            // made once, shared
let mut reader = ScanReader::new(&shape);
submitter.scan(&mut reader, &ScanArgs::default())?;   // to the executor
while reader.next_row()? {
  let row = reader.row();                             // laid out by the record
}
```

- **A shape** (`ScanShape`) is a table and the record its rows are
  read into, as an `OpShape` is for key operations. The executor
  keeps scans of each shape it has run, made once on its connection,
  and lets them go once nobody holds the shape. A run after the first
  allocates nothing there.
- **A reader** (`ScanReader`) is the application thread's end of the
  scan: the row, laid out by the record, and the batches given to it
  and not yet handed back. A reader is used again and again.
  `submitter.scan` on a reader whose run is not over is refused with
  `IC_ERROR_SCAN_ACTIVE`.
- **Credit**: when a receiver's batch is complete, the executor moves
  its buffer to the reader without copying a row, and wakes the reader
  if it waits. The reader reads the batch's rows and, when it moves on
  to the next batch, hands the buffer back.
- **When a receiver goes on**: only once the reader has handed back
  the buffer its batch is in, whatever the lock (the author,
  2026-10-16). A locking scan's rows thus stay locked while the
  application reads them, as on a connection, and one rule serves
  every scan. A receiver has at most one batch with the reader, so
  memory stays within the receivers times the batch bytes. A slow
  reader stalls only its own receivers: the executor's loop goes on
  with everything else.
- **Reading ahead** (the author, 2026-10-16): a committed read is made
  faster by the continuous scan, which keeps fetching a fragment's
  rows ahead (chapter 05 §7.2, phase 10). Short of that, a flag of
  iClaustron's own, `ScanArgs::read_ahead`, lets a committed read's
  receiver go on as soon as its batch has moved to the reader, so a
  receiver has up to two batches out, one with the reader and one
  coming, and memory doubles. It is off by default, since a scan that
  is closed early will have read ahead for nothing. A locking scan
  with it is refused (`IC_ERROR_NOT_SUPPORTED`), since its locks would
  go before its rows were read. The flag is for scans through an
  executor, and refused on a connection, where the application already
  holds each batch and hands it back itself.
- **Waking**: the reader sleeps on a condition of its own while it has
  no batch. A buffer handed back wakes the executor through its inbox,
  on a list of its own, which neither the in-flight limit nor a full
  request list holds back.
- **Arguments**: the `ScanArgs` of a connection's scan. `trans` and
  `callback` are refused with `IC_ERROR_NOT_SUPPORTED`: a scan on an
  executor is in no transaction of the application's, and its batches
  go to the reader. `timeout_ms` counts from the submit.
- **Limits**: at most `ExecutorOptions::scans` scans run at once
  (64 by default), and scans wait in a queue of their own. A scan
  waiting for room then never holds a transaction back, nor the
  reverse. A parked scan counts against `scans`, not against
  `in_flight`.
- **The end**: `next_row` gives `Ok(false)` once the scan has read to
  the end, and its error once it has failed. `reader.close()` ends a
  run early and waits for the executor to finish it, so that the
  reader can run again. Dropping a reader ends its run without
  waiting. A stopping executor closes its scans with
  `IC_ERROR_EXECUTOR_STOPPED`.
- A Rust stream comes later, over the same reader.

**The C ABI**, by the rules below:

- `IC_SCAN_ID` (`uint32_t`) names a scan in its connection, and
  `IC_SCAN_BATCH_ID` (`uint64_t`) a batch: the scan and its
  receiver's id in the run.
- `ic_scan_args_init(&args, sizeof args)` fills an `IC_SCAN_ARGS`:
  `lock` (`IC_SCAN_LOCK_COMMITTED`, `IC_SCAN_LOCK_SHARED`,
  `IC_SCAN_LOCK_EXCLUSIVE`), `trans` (`IC_NO_TRANS` for none),
  `parallelism`, `batch_rows`, `batch_bytes`, `partition`
  (`IC_NO_PARTITION` for none), `timeout_ms`, `read_ahead`,
  `callback` and `user_ref`.
- On a connection: `ic_apid_scan_create(conn, def, rec, &scan)`;
  `ic_apid_scan_free(conn, scan)`;
  `ic_apid_conn_start_scan(conn, scan, &args)`;
  `ic_apid_conn_close_scan(conn, scan)`; `ic_apid_scan_state`,
  `_is_done`, `_error`, `_rows_read`; and
  `ic_apid_scan_row(conn, scan, &len)`, the scan's row, valid until
  the scan is freed.
- Batches: `ic_apid_conn_get_next_scan_batch(conn, &batch)`;
  `ic_apid_scan_batch_rows(conn, batch)`; `ic_scan_batch_scan(batch)`,
  the scan a batch is of;
  `ic_apid_conn_next_scan_row(conn, batch, &more)` and
  `_next_scan_row_into(conn, batch, row, len, &more)`;
  `ic_apid_conn_release_scan_batch(conn, batch)`.
- Synchronous: `ic_apid_conn_next_row(conn, scan, &more)`,
  `_next_row_into(conn, scan, row, len, &more)` and
  `ic_apid_conn_next_batch(conn, scan, &batch, &more)`.
- The callback is `void (*IC_SCAN_CALLBACK)(IC_APID_CONNECTION *conn,
  IC_SCAN_BATCH_ID batch, void *user_ref)`, called through a
  trampoline as a query's is.
- Through an executor: `ic_scan_shape_create(def, rec, &shape)` and
  `ic_scan_shape_free(shape)`;
  `ic_scan_reader_create(shape, &reader)` and
  `ic_scan_reader_free(reader)`;
  `ic_apid_submitter_scan(sub, reader, &args)`;
  `ic_scan_reader_next_row(reader, &more)`, `_next_row_into`,
  `ic_scan_reader_row(reader, &len)`, `_rows_read`, `_error`,
  `_is_done`, and `ic_scan_reader_close(reader)`.
- `IC_EXECUTOR_OPTIONS` gains `scans` and `IC_EXECUTOR_STATS` gains
  `scans`, at the end. A program built against 0.1's header passes the
  shorter structs, and gets the fields it knows: the first structs to
  grow since 0.1, so the library now reads and writes only the fields
  a struct's size holds.
- The scan errors become C constants: `IC_ERROR_SCAN_ACTIVE` (7161),
  and NDB's `IC_NDB_ERROR_TOO_MANY_SCANS` (245),
  `IC_NDB_ERROR_LOCK_TIMEOUT` (266, there already),
  `IC_NDB_ERROR_SCAN_LOCK_TIMEOUT` (274), `IC_NDB_ERROR_SCAN_IDLE`
  (296) and `IC_NDB_ERROR_SCAN_NODE_FAILURE` (4028).

### Taking scanned rows over (phase 8.5; built 2026-10-16)

A locking scan started on a transaction (`ScanArgs::trans`) hands the
row last read over to that transaction, as MySQL's `SELECT ... FOR
UPDATE`, `UPDATE` and `DELETE` by scan do:

```rust
conn.start_scan(scan, &ScanArgs { lock: ScanLock::Exclusive, trans: Some(tid), ..ScanArgs::default() })?;
while conn.next_row(scan)? {
  if wanted(conn.scan_row(scan)) {
    // ... the new values into the query's attribute row ...
    conn.update_scan_row(qid, scan, &TakeoverArgs::default())?;
  }
}
conn.commit_transaction(tid)?;
```

- `lock_scan_row`, `update_scan_row` and `delete_scan_row` each define
  a query on the scan's transaction that acts on the row last read
  from a batch still with the application. The query is an ordinary
  one over the scanned table, and completes as any query does. Its key
  is not taken from its key row but is the row's, as the data node gave
  it with the row. A lock taken over reads the attribute record's
  columns, shared from a shared-lock scan and exclusively from an
  exclusive one, as the reference does. An update writes the attribute
  row's values, its key columns left out. The lock is the
  transaction's from then on, to its commit or rollback.
- **`TakeoverArgs`**: `abort_option` (by default the transaction rolls
  back if the takeover fails, as the reference's takeovers do),
  `user_ref`, `callback` and `binding`, as for a query.
- **The batch waits for its takeovers.** Handing a batch back is
  always allowed. Its receiver asks for more, which releases the
  batch's locks, only once every takeover of the batch has completed,
  confirmed or failed (chapter 05 §7.2). A close's stop waits likewise.
  `next_row`, waiting for a batch, sends the takeovers defined first;
  a program reading a batch at a time sends them itself, as it sends
  any query.
- **Refused**: a scan with no transaction (`IC_ERROR_NOT_SUPPORTED`):
  its rows' keys were not asked for. No row read yet, or its batch
  handed back (`IC_ERROR_NO_SCAN_ROW`, 7162). A query through an index
  (`IC_ERROR_NOT_SUPPORTED`), or over another table
  (`IC_ERROR_KEY_RECORD`). A transaction no longer open
  (`IC_ERROR_TRANSACTION_ACTIVE`).
- **The transaction may commit while its scan still runs.** The
  coordinator checks a scan's owning record each time it uses it, so
  no harm comes of it. The scan goes on with its own locks, and
  takeovers are refused from then on. Closing the scan first, as MySQL
  does, is the usual order.
- **C**: `ic_takeover_args_init(&args, sizeof args)` for an
  `IC_TAKEOVER_ARGS` (`abort_option`, `callback`, `user_ref`), and
  `ic_apid_conn_lock_scan_row(conn, q, scan, &args)`,
  `_update_scan_row` and `_delete_scan_row`; `IC_ERROR_NO_SCAN_ROW`.
- Not through an executor: its requests are whole transactions, and a
  takeover needs one that stays open across calls (kept for later).

### Index scans (phase 8.7; agreed with the author and built 2026-10-17)

A scan of an ordered index reads the rows of its table whose index
columns lie in the ranges given, and is made once and run many times
as a table scan is:

```rust
let index = conn.index_bind(db, "ix_val", "scan")?;    // an ordered index
let key_rec = Record::default_for(&table, Some(&[val]))?; // its columns
let scan = conn.create_index_scan(&index, &key_rec, &rec)?;
let range = ScanRange {                // val from 100 to 200, both in
  low_columns: 1, low_inclusive: true,
  high_columns: 1, high_inclusive: true,
  range_no: 0,
};
conn.add_scan_range(scan, &range, &low_row, &high_row)?;
conn.start_scan(scan, &ScanArgs { ordered: true, ..ScanArgs::default() })?;
while conn.next_row(scan)? {
  let row = conn.scan_row(scan);       // in the index's order
}
```

- **`create_index_scan(&index, &key_rec, &rec)`**: an ordered index
  (another is refused, `IC_ERROR_NOT_SUPPORTED`); a key record over
  its table holding every column of the index, the convention the key
  records of `create_unique_query` follow (`IC_ERROR_KEY_RECORD`);
  and the record the rows are read into, over the table.
- **Ranges as rows** (the author, 2026-10-17, choosing between rows of
  the key record, as the reference's bounds by record are given, and
  a bound for each column, as its older interface has them):
  `add_scan_range(scan, &range, low_row, high_row)`, both rows laid
  out by the key record. `ScanRange` says how many of the index's
  leading columns each bound takes from its row (`low_columns`,
  `high_columns`; 0 for no bound on that side), whether a bound is in
  the range (`low_inclusive`, `high_inclusive`), and the range's
  number (`range_no`, 0 to 4095). A bound is compared as the index
  orders its rows, column by column, so the low bound (7, 3) takes in
  (7, 3) if inclusive, then (7, 4), (8, 0) and so on. A NULL in a
  bound is a bound at NULL, which comes before every value. The range
  is encoded at once, as the request carries it (chapter 05 §7.2), and
  the rows are not kept. When both bounds take the same columns with
  the same values and both are inclusive, the range goes as
  equalities, as the reference sends it.
- **A run takes the ranges added before it** and the next run is
  given its own. A run given none reads the whole index, as one open
  range. A range that cannot be sent is refused with
  `IC_ERROR_BAD_RANGE` (7163): its number above 4095, more columns
  than the index has, or more than 65 535 words of bounds.
- **`ScanArgs::ordered`**: the rows in the index's order across
  fragments. Every fragment is scanned at once, a receiver each,
  whatever `parallelism` says, and `next_row` merges them. It needs a
  row or the end from every receiver before it gives one (chapter 05
  §7.2). Each column is compared as the data nodes compare it.
  Numbers, decimals, dates and times compare by value, binary strings
  by their bytes, and a character column by its collation's order,
  from the description the data nodes give (chapter 06 §8.6). The
  record must hold every column of the index (`IC_ERROR_KEY_RECORD`).
  An index with a column whose order is not known here, an old
  decimal or a character column whose collation could not be
  described or weighs a character by its neighbours, refuses an
  ordered run (`IC_ERROR_NOT_SUPPORTED`). An ordered run is read only
  with `next_row` and `next_row_into`: its batches go on no ready
  list, so a callback and `next_batch` are refused
  (`IC_ERROR_NOT_SUPPORTED`). With several ranges the rows come range
  by range, and the numbers must rise in the order the ranges were
  added (`IC_ERROR_BAD_RANGE`).
- **`ScanArgs::descending`**: each fragment from the high end, and an
  ordered run's merge too; the ranges keep their order. `ordered` and
  `descending` are refused on a table scan (`IC_ERROR_NOT_SUPPORTED`).
- **Range numbers**: a run with more than one range reads each row's
  range number with it (chapter 05 §7.2), and `conn.scan_range_no(scan)`
  gives the number of the row last read. In a run with one range it
  is that range's number.
- **Pruning**: a run whose every range fixes the table's
  distribution key to the same partition, both bounds taking every
  distribution key column with the same values, scans that partition
  alone, as the reference prunes (chapter 05 §7.2). A key whose
  partition cannot be worked out here, such as one with a character
  column whose collation could not be described, is not pruned.
  `ScanArgs::partition` names one partition by its id, and wins.
  `Scan::parallelism` gives the receivers a run had, one when pruned.
- **Takeovers** as from a table scan (8.5): an index scan's rows come
  with the table's keys.
- **Through an executor** (phase 8.7b, 2026-10-17):
  `ScanShape::new_index(&index, &key_rec, &rec)` makes a shape over
  the index; `reader.add_range(&range, low_row, high_row)` adds a range
  to the reader's next run, encoded at once, and `reader.range_no()`
  gives the row's range number. `ScanArgs::ordered` and `descending`
  are as on a connection, and refused for a shape over a table
  (`IC_ERROR_NOT_SUPPORTED`).

  ```rust
  let shape = ScanShape::new_index(&index, &key_rec, &rec)?;
  let mut reader = ScanReader::new(&shape);
  reader.add_range(&range, &low_row, &high_row)?;
  submitter.scan(&mut reader, &ScanArgs { ordered: true, ..ScanArgs::default() })?;
  while reader.next_row()? {
    let row = reader.row();            // in the index's order
  }
  ```

  The ranges are left in the reader's feed for the executor to take as
  it starts the run, under the lock that says the run is still the
  reader's, and the emptied set it leaves there takes the reader's
  next, so a run after the first allocates nothing for them. They are
  not part of the run's request, which goes through the executor's
  inbox by value and is kept small. **The reader merges an ordered
  run, not the executor**: a batch moves to the reader without a copy,
  a receiver has at most one there, and the merge needs one from each,
  so the executor's loop does no work per row for any reader. The
  executor's scan of an ordered run is unordered, over every fragment,
  and each batch goes with its receiver's place and whether it is the
  receiver's last. The reader takes the row that comes first once
  every receiver has a batch with a row or has ended, handing a
  batch back once its rows are read, as a connection's merge does.
  With `read_ahead` a receiver's next batch may come before its last
  is read, and waits with the reader.
- **C** (phase 8.8, 2026-10-17): `IC_SCAN_RANGE`, filled by
  `ic_scan_range_init(&range, sizeof range)` (no bounds, range 0), with
  `low_columns`, `low_inclusive`, `high_columns`, `high_inclusive` and
  `range_no`. On a connection: `ic_apid_index_scan_create(conn, index,
  key_rec, rec, &scan)`; `ic_apid_conn_add_scan_range(conn, scan,
  &range, low, low_len, high, high_len)`, a bound the range does not use
  NULL with length 0, the rows copied into the encoded range and not
  kept; `ic_apid_scan_range_no(conn, scan)`. Through an executor:
  `ic_scan_shape_create_index(index, key_rec, rec, &shape)`,
  `ic_scan_reader_add_range(reader, &range, low, low_len, high,
  high_len)` and `ic_scan_reader_range_no(reader)`. `IC_SCAN_ARGS`
  gains `ordered` and `descending` at its end; it is new in 0.2, not
  yet released, so no shorter one is taken. `IC_ERROR_BAD_RANGE`
  (7163).

### Conditions and assignments (phase 9.1; agreed with the author 2026-10-20)

A condition is built bottom-up, as a tree, and compiled whole (the
author, 2026-10-20, choosing among the old builder's subroutine ids
handed out top-down and its values at memory addresses,
`legacy-c/include/ic_apid.h:1123-1217`; this tree; and groups opened
and closed in the order a condition is written, as MySQL compiles its
conditions). The old builder's model stays, values and conditions
between them, without subroutine ids for the caller to keep:

- **Values** each return an id: a column, `column(id)`; a constant,
  `constant(&rec, row, id)`; and computed values, `add(a, b)` and
  `subtract(a, b)`, the rest of them later.
- **Constants from rows** (the author, 2026-10-20, choosing between
  rows, as the ranges of 8.7 are given, and typed values converted to
  the compared column's type): `constant(&rec, row, id)` is the value
  of column `id` in a row laid out by `rec`, a record over the
  condition's table. It is encoded at once, as a write encodes it, and
  the row is not kept. Every type a record can carry is a constant,
  with nothing new to encode, and a value its column cannot hold
  cannot be in the row. A term comparing a column with a constant
  needs them of one type, length, precision, scale and collation, as a
  column compared with a column does (chapter 05 §9.3); others are
  refused at `finish`. A NULL in the row is a NULL constant, and a
  term with one is unknown, as SQL has it. The constants a computed
  value or an assignment adds or subtracts, as in `val + 1`, are plain
  integers, as the registers hold them.
- **Terms** each return an id: `compare(op, a, b)` with `=`, `<>`,
  `<`, `<=`, `>` and `>=`, `is_null(a)` and `is_not_null(a)`.
- **Joined** by `and(x, y)`, `or(x, y)` and `not(x)`, each returning
  an id too.
- **`finish(top)` compiles** the tree under `top`. With all of it in
  hand the compiler takes a column test (chapter 05 §9.3) wherever a
  term compares a column with a constant or with a column of the same
  type, flattens nested ANDs and ORs into one level of jumps with
  SQL's NULL logic, as MySQL's programs have them (§9.6–9.7), and
  places registers only where values are computed. More than eight
  values live at once is `IC_ERROR_CONDITION_TOO_COMPLEX` (7130).
- **Assignments**: `assign(column, value)`, the value a constant from
  a row or a column plus or minus an integer, with a condition of its
  own if wanted (the old `IC_CONDITIONAL_ASSIGNMENT`).
- **A program is made once and used again** (the author, 2026-10-20):
  only its inputs change from one operation to the next, up to 16
  integers of 64 bits (chapter 05 §9.5). In the tree an input is a
  value, `input(n)` with n from 0 to 15, compared with an integer
  column through registers, or added to one. The program knows the
  inputs it reads, and each operation sends them all, since an input
  left unset holds an earlier operation's. A constant from a row stays
  in the program; a value that changes between operations is an input.
- **A program goes beside the records, its inputs beside the rows**
  (the author, 2026-10-20, choosing between a program given with each
  operation, by reference, and one kept in what is made once). A
  program is shared (`Arc<Program>`) and made for one table.
  - On an executor a shape takes it: `shape.with_program(&program)`
    makes a shape of the same records that runs it, for `OpShape` and
    `ScanShape` alike, and the executor encodes the program once for
    the shape. A plain update and a conditional one are two shapes.
  - On a connection a query and a scan keep it until it is changed:
    `query.set_program(Some(&program))` and
    `conn.set_scan_program(scan, Some(&program))`; `None` takes it
    off.
  - The inputs: `set_input(n, value)` on a `KeyOp`, an `ApidQuery` and
    a `ScanReader`, and `conn.set_scan_input(scan, n, value)`. Each
    holds its 16, 0 until set and kept until changed, and sends those
    its program reads with every operation or run, so none is left
    to an earlier operation's.
  - A program goes on key reads, updates and deletes and on scans,
    the basic set's operations (chapter 06 §9.1); one with assignments
    only on an update. Others are refused when the operation is
    defined.
- **Reads after an update** (the author, 2026-10-20, choosing between
  a record of the columns read after the program and the program's
  outputs, chapter 05 §9.5): a record of their own, beside the
  program. On an executor `shape.reading_after(&after_rec)` makes a
  shape that reads them, and on a connection
  `query.set_reads_after(Some(&after_rec))` keeps it until changed.
  The values come back as a read's do, after the program and its
  assignments, into a row of their own laid out by that record,
  `after_row()` on a `KeyOp` and an `ApidQuery`: any column of any
  type, as the AUTO_INCREMENT counter's new value comes (chapter 05
  §9.6). Only an update reads after. The outputs may come beside it
  later.

- **As built (2026-10-20)**, `ic_apid::program`:
  `ProgramBuilder::new(&table)`; values `column(id)`,
  `constant(&rec, row, id)`, `integer(i64)`, `input(n)`, `add`,
  `subtract`; conditions `compare(Cmp, a, b)`, `is_null`,
  `is_not_null`, `and`, `or`, `not`; `assign(column, value)` and
  `assign_if(column, value, cond)`; `finish(Some(top))`, or
  `finish(None)` for a program that only assigns, giving an
  `Arc<Program>`. A missed condition refuses with 6000 where the
  operation aborts on error and 626 where it ignores errors; a scan's
  always 626, which passes the row over. An update's attribute row is
  written after the program, after the program's own constants, so a
  conditional update is a program with only a condition and the
  values in the row. An update may read after with no program, which
  then only accepts. Refused when the operation is defined
  (`IC_ERROR_NOT_SUPPORTED`): a program on an insert or a write, one
  that assigns on a read or a delete, reads after on anything but an
  update, and a program through a unique index or on a takeover of a
  scanned row, for later. A unique `OpShape` refuses `with_program`
  and `reading_after`.

C follows the Rust API by the ABI's rules below, as the scans' did.

### AUTO_INCREMENT (phase 9.2; agreed with the author 2026-10-20)

Values are asked for, not filled in (the author, 2026-10-20, choosing
between an explicit call and an insert that fills a NULL
AUTO_INCREMENT column as MySQL does):

- **`conn.auto_increment(&table) -> u64`**: the next value of the
  table's AUTO_INCREMENT column, from a range reserved ahead; when the
  range is used up, one counter update reserves the next (chapter 05
  §16.5), a round trip in the call. The application puts the value in
  its row.
- **`conn.auto_increment_seen(&table, value)`**: after an insert with
  a value of the application's own, so that the counter moves past it,
  only ever up.
- **`conn.auto_increment_peek(&table) -> u64`** (the author,
  2026-10-20, choosing between it and none): the counter as it stands,
  the next value no client has reserved, by one shared read of the
  counter row (chapter 05 §16.5), the range neither locked nor
  touched. Advisory: not the next value this process hands out from
  its range, and stale once any client refills. MySQL servers read it
  for the `AUTO_INCREMENT` that `SHOW TABLE STATUS` reports; the
  exit's test reads it to see an explicit value move the counter.
- Defining an insert stays as it is, packing a request without a
  round trip; filling the column as MySQL does may come later as a
  helper over these.

- **One range per table for the whole process** (the author,
  2026-10-20, choosing between a range per connection, as the
  reference API keeps one per connection object, and one per process,
  as MySQL servers keep one per table under a guard, chapter 05 §16.5):
  the table's description, shared by every connection and executor,
  holds it under a mutex. Taking a value is a short step under the
  lock; the thread that finds the range used up refills it, holding
  the lock for that round trip while others wait, as MySQL's guard
  does. So the values a process hands out come close to in order
  across its threads, and gaps and refills do not grow with the number
  of threads.

- **The refill goes on a connection the process keeps for the
  counters** (built 2026-10-20, phase 9.2a), made at first use and
  used for one counter operation at a time under a mutex of its own,
  taken under a table's range and never the other way round. Not on
  the caller's connection: flushing it would send the queries the
  application had defined and not yet sent, and its poll would run
  the application's callbacks, which may themselves ask for values of
  the table whose lock the thread holds. An attempt whose transaction
  has not ended a second after its own wait for replies should have
  ended it gives the connection up, and the next makes another.

- **How many values a refill reserves** (the author, 2026-10-20, Q13,
  choosing among one size for the process, a size per table beside
  it, and a block per call beside both): all three.
  `GlobalOptions::auto_increment_prefetch`, **4096** by default, eight
  times the 512 MySQL servers take by default (chapter 05 §16.5);
  `table.set_auto_increment_prefetch(n)` on the shared description, for
  that table alone; and `conn.auto_increment_block(&table, n)`, the
  first of `n` values in a row, reserved together, for an insert of
  many rows, as a MySQL server raises its prefetch to the rows of a
  bulk insert. A block the range left holds is taken from it; one it
  does not is reserved by a refill of its own, of at least `n`.

- **Step and offset, one pair for the process** (the author,
  2026-10-20, choosing among none, one pair for the process, and a
  pair per table): `GlobalOptions::auto_increment_step` and
  `GlobalOptions::auto_increment_offset`, 1 and 1 by default, as
  MySQL's `auto_increment_increment` and `auto_increment_offset`
  (chapter 05 §16.5). A refill reserves prefetch × step; the next value
  is the least k × step + offset above the last handed out, an offset
  above the step counting as 1; a block of `n` is `n` values a step
  apart. They are what tell the clusters of a replication ring apart,
  each with its own counter, so they belong to the global, one cluster
  each, and are set as that cluster's MySQL servers are. Within one
  cluster, clients with different steps still never share a value, as
  each reserves its own stretch of the counter. The hidden `$PK` always
  takes 1 and 1, as MySQL servers do.

- **The value is returned as it is** (the author, 2026-10-20, choosing
  between that and checking it against the column's type, as MySQL
  does, chapter 05 §16.5): an AUTO_INCREMENT column narrower than 64
  bits is the schema's error, in the author's view, and fitting a
  value to such a column is the application's.

- **A temporary error on the counter is retried inside the call** (the
  author, 2026-10-20, choosing between that and returning it at once):
  repeating a counter update is always safe, as an attempt whose
  outcome is unknown at worst leaves a gap, never a duplicate. Unlike
  MySQL servers' 100 attempts 30–36 ms apart (chapter 05 §16.5), the
  first pause is short, **100 µs, doubled after each failure**; once
  **3.6 s** have passed since the first attempt the call fails with the
  last error. A pause that would carry past that is cut to end there,
  for one last attempt: some seventeen attempts at most, fewer as each
  round trip counts too. The table's lock is held throughout, so
  threads waiting for values wait behind the one retrying rather than
  each trying the troubled counter row in turn. An error that is not
  temporary is returned at once.

- **Through an executor, the same calls on the submitter** (the
  author, 2026-10-20, choosing between them and calls on the table's
  description taking a connection or a submitter through a trait):
  `submitter.auto_increment(&table)`,
  `submitter.auto_increment_block(&table, n)`,
  `submitter.auto_increment_seen(&table, value)` and
  `submitter.auto_increment_peek(&table)`. They are the connection's:
  the calling thread takes from the shared range itself, and a
  refill, or an explicit value past the counter, goes on the process's
  counter connection as from a connection, not through the executor.
  A connection and an executor in one process share each table's
  range. Asked from a callback on the executor's own thread, a refill
  holds the executor for its round trip, up to 3.6 s while it retries;
  nothing waits for itself, so the calls are not refused there (they
  were to be, while a refill was to go through the executor, revised
  2026-10-20 in 9.2a).

- **A table without a primary key shows its hidden key as the
  dictionary has it** (the author, 2026-10-20, choosing between that
  and hiding it, with inserts filling it themselves and its rows
  reached only by a scan's takeover): `$PK` stays an ordinary last
  column, BIGUNSIGNED, the primary key and the table's AUTO_INCREMENT
  column (chapter 05 §16.5). An insert takes its key from
  `auto_increment(&table)`, step and offset 1 and 1, and puts it in its
  key record; a scan reads `$PK` as any column, and reads, updates and
  deletes by that key work as on any table, as do takeovers.
  `table.hidden_key() -> Option<u32>` names the column, so that tools
  listing columns can leave it out. Nothing else is new: records, key
  operations, scans and takeovers over `$PK` already work.

C follows by the ABI's rules, a status returned and the value through
a pointer: `ic_apid_conn_auto_increment`,
`ic_apid_conn_auto_increment_block`,
`ic_apid_conn_auto_increment_seen` and
`ic_apid_conn_auto_increment_peek`, the same four as
`ic_apid_submitter_auto_increment…`,
`ic_table_def_set_auto_increment_prefetch`, and
`auto_increment_prefetch`, `auto_increment_step` and
`auto_increment_offset` at the end of `IC_GLOBAL_OPTIONS`, and
`auto_increment` and `hidden_key` flags at the end of `IC_FIELD_INFO`,
where their sizes keep older programs working. As built (2026-10-20,
9.2b): `IC_GLOBAL_OPTIONS` is written and read field by field, each
only where the size the program gave holds it, so a program built
against 0.1's header, 16 bytes long, keeps the defaults for the rest,
as `IC_EXECUTOR_OPTIONS` does; the two flags of `IC_FIELD_INFO` took
what was its padding, so its size is 0.1's, 56 bytes. A stopped
executor's submitter refuses the calls with `IC_ERROR_EXECUTOR_STOPPED`,
as it refuses everything, though they never reach the executor.

### Errors

`IcError` is a code: 7000 and up iClaustron's own, small positive codes
operating system errors, others NDB codes as the data nodes report
them. Every error has a category (`User`, `Internal`, `External`), a
severity (`Warning`, `Temporary`, `Error`, `Stop`), and a text;
`is_temporary()` says whether the same request may well succeed if
tried again, as for a node failure or an overload. An unknown outcome,
4012 among them, counts as temporary, as NDB classes it: the request
may be tried again, but the transaction may also have committed, so a
write is tried again only once the application knows it did not, or
when doing it twice does no harm (user guide, "When to try again").

### The limits of 0.1

(The executor, above, came after 0.1.)

No scans, no interpreted conditions, no blob columns (bound tables may
have them; records leave them out, deletes are refused), no DDL, no TLS,
at most 4 711 user threads per process (RonDB's limit for an API
node), no events.

## The C ABI

### Rules

- Every exported symbol starts with `ic_`, every type with `IC_`; every
  type that crosses is `#[repr(C)]` or opaque.
- **Handles**: `IC_APID_GLOBAL`, `IC_APID_CONNECTION`, `IC_TABLE_DEF`,
  `IC_INDEX_DEF`, `IC_RECORD` are opaque pointers made by a
  `..._create`, `..._connect` or `..._bind` function and given back to
  a `..._free` function. A table or index handle holds the description
  alive; freeing it does not unbind.
- **Ids**: a query and a transaction are named by a `uint32_t` within
  their connection (`IC_QUERY_ID`, `IC_TRANS_ID`), as in Rust. An id
  that no longer names a live one, freed or closed, is refused with an
  error, never followed.
- **Rows (Q10, applied 2026-10-14)**: the query owns its rows; C gets
  pointers to them, `ic_apid_query_key_row(conn, q, &len)` and
  `ic_apid_query_attr_row(conn, q, &len)`, valid until the query is
  freed. No copy, and no pointer into the caller's memory. The
  application writes the key row (and for a write the attribute row)
  before it defines the query, and reads the attribute row once the
  query has completed; between define and completion the rows are the
  library's. The synchronous helpers take the caller's rows and copy.
- **Results**: a function that can fail returns `int32_t`, 0 or the
  error code, and gives what it makes through an out pointer. A null
  handle or out pointer is `IC_ERROR_NULL_POINTER` (7157); text that is
  not UTF-8, or a value given as text that does not fit its field,
  `IC_ERROR_BAD_TEXT` (7158). A function that gives a value rather
  than a code (a row pointer, a state, a hint) gives a value that says
  "none" instead: NULL, `IC_QUERY_UNKNOWN`, `IC_HINT_ANY`.
- **Errors**: `ic_error_category(code)`, `ic_error_severity(code)`,
  `ic_error_is_temporary(code)`, and `ic_error_message(code, buf, len)`
  copying the text into the caller's buffer.
- **Strings** in are `const char*`, NUL-terminated, copied. Strings out
  (a table's and a field's name) are valid until the handle is freed.
- **Option and argument structs** begin with their own size, filled by
  `..._init(&s, sizeof s)`, so that a later release can add fields at
  the end without breaking a program built against this one; a struct
  the library fills (`IC_FIELD_INFO`) is given with its size likewise.
- **Threads**: a global may be used from any thread. A connection, and
  every query and transaction in it, by one thread at a time. Callbacks
  run on the thread that polls.
- **Panics**: a panic inside the library is caught at the C entry and
  returned as `IC_ERROR_INTERNAL_PANIC` (7129); the connection it went
  through is marked unusable, and every later call on it returns the
  same.
- **Versions**: `ic_api_version(&major, &minor, &patch)`. The library
  is `libiclaustron`, shared and static; the shared one's soname
  carries the major version (`libiclaustron.so.0`), and on macOS its
  install name is where it was installed. `cargo xtask install
  [prefix]` builds it and installs the libraries, the header and
  `iclaustron.pc` for pkg-config.
- The header is generated by cbindgen from `ic_capi` and checked in;
  `cargo xtask header` regenerates it into `target/` and diffs. Its
  top states these rules; each function's comment says what is
  particular to it: its errors, where it blocks, what it hands over and
  for how long.
  Enum values are appended, never renumbered.
- Platforms for 0.1 (Q7, applied 2026-10-14): Linux on x86_64 and
  aarch64, macOS on aarch64.

executor harmlessly: it refuses.

### Callbacks

The C callback is `void (*IC_APID_CALLBACK)(IC_APID_CONNECTION *conn,
IC_QUERY_ID query, void *user_ref)`, set in the read or write arguments
with its `user_ref`. The C ABI gives Rust one trampoline as the query's
callback and keeps the C function in the query's `binding` word; when
the query completes, the trampoline calls the C function with the
connection's handle, the query and the `user_ref`. Inside, the C
callback may call any `ic_apid_conn_*` and `ic_apid_query_*` function
on that connection except a poll or flush, which does nothing, and must
not free the connection.

### Example in C, asynchronous

```c
IC_GLOBAL_OPTIONS opts;
IC_APID_GLOBAL *global;
IC_APID_CONNECTION *conn;
IC_TABLE_DEF *t;
IC_RECORD *rec;
IC_QUERY_ID q;
IC_TRANS_ID tr;
IC_READ_KEY_ARGS args;
uint8_t *key, *row;
size_t len;
int32_t ret;

ic_global_options_init(&opts, sizeof opts);
if ((ret = ic_apid_global_connect("localhost:1186", "example", &opts,
                                  &global)) != 0)
  goto error;
ic_apid_global_wait_for_started(global, 30000, 0, NULL);
if ((ret = ic_apid_global_create_connection(global, &conn)) != 0 ||
    (ret = ic_apid_conn_table_bind(conn, "test", "t1", &t)) != 0 ||
    (ret = ic_record_create_default(t, NULL, 0, &rec)) != 0 ||
    (ret = ic_apid_query_create(conn, t, rec, rec, &q)) != 0)
  goto error;
key = ic_apid_query_key_row(conn, q, &len);
ic_record_put_text(rec, A_ID, "42", key, len);
ic_read_key_args_init(&args, sizeof args);
args.kind = IC_READ_KIND_COMMITTED;
if ((ret = ic_apid_conn_start_transaction(conn,
            ic_apid_conn_hint_for_key(conn, t, rec, key, len), t,
            &tr)) != 0 ||
    (ret = ic_apid_conn_read_key(conn, q, tr, &args)) != 0 ||
    (ret = ic_apid_conn_commit_transaction(conn, tr)) != 0)
  goto error;
while (!ic_apid_transaction_is_done(conn, tr))
  ic_apid_conn_flush(conn, 100, 1, NULL);
if ((ret = ic_apid_query_error(conn, q)) != 0)
  goto error;
row = ic_apid_query_attr_row(conn, q, &len);
/* ... use the row ... */
ic_apid_conn_close_transaction(conn, tr);
```
