Today a thread pipelines its own work: it defines many operations, sends once per node and collects replies in poll, with callbacks defining the next batch. That is how one thread reaches 2.6 million reads a second, but new work can only come from that thread. The proposal: an executor is an ordinary user thread. It must accept new queries while earlier ones are in flight, so it listens to replies from the data nodes and requests from application threads. The key point: both arrive in the same inbox, under one mutex and one condition, so the executor waits in exactly one place and wakes for whichever comes first. No select over two channels, no forwarding thread.
