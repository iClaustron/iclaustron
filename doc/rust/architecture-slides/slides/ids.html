How a reply finds its transaction

Each request carries a number we choose, and the data node sends it back in its reply. We choose it to be the transaction's place in our own table, so one lookup finds it.

1 · WE SEND

TCKEYREQ

carries our number: place 3

2 · DATA NODE

Keeps it

with its own record of the transaction

3 · REPLY

TCKEYCONF

first word: place 3

4 · ONE LOOKUP

table[3]

is our transaction: no search, no lock

Rows work the same way. A row (TRANSID_AI) carries the query's id instead, and finds the query the same way.

Late replies are caught. Every reply also carries the transaction id; one left over from an earlier use of place 3 does not match, and is dropped.

The protocol lets the API put its own number in a request, and the data node echoes it in every reply about that transaction. We don't use a pointer or a hash key there; we use the transaction's position in the thread's own table, so finding it is a single array index. Two details for those who ask: the number's top bit marks it as ours and its lowest bit is left for the protocol's acknowledgement flag. The block number in the signal header picks which user thread gets the reply in the first place. The exact bit layouts are on the architecture page.
